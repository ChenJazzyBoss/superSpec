# superSpec: Verify

禁止在没有新鲜验证证据的情况下声明完成。

## 使用时机

当你想要声明"完成了"、"测试通过了"、"构建成功了"时，使用此技能。

## 5 步验证流程

<EXTREMELY-IMPORTANT>
你必须按顺序完成以下 5 步，不可跳过。
</EXTREMELY-IMPORTANT>

1. **识别**：什么命令能证明这个结论？
2. **运行**：执行完整命令（重新运行，不是回忆之前的结果）
3. **读取**：完整输出，检查退出码，计数失败
4. **验证**：输出是否支持结论？
5. **只有这时**：才能得出结论

## HARD-GATE

<HARD-GATE>
没有新鲜验证证据 = 不允许声明完成
没有例外，没有"就这一次"
</HARD-GATE>

## 三维度验证

验证实现是否符合 spec 时，检查三个维度：

- **完整性**：所有需求都有对应实现
- **正确性**：实现符合 spec 意图
- **一致性**：代码结构与 spec 结构对应

## spec 校验命令

spec 相关验证必须运行：

```bash
node .superspec/scripts/validate.js .superspec/specs/<name>/spec.md
```

检查输出中的 valid 字段。

## 对抗性验证

派发对抗性验证子代理：

- 尝试推翻结论
- 寻找反例
- 检查边界条件
- 验证错误处理

只有子代理无法推翻时，才确认完成。

## 跳步红线

| 跳步借口 | 现实 |
|----------|------|
| "应该没问题了" | 运行验证命令，拿证据 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "linter 通过了" | linter ≠ 校验器 |
| "子代理说成功了" | 必须独立验证 |
| "之前测试通过了" | 之前 ≠ 现在，重新运行 |
| "测试太多了，挑几个跑" | 选择性测试会隐藏失败 |
| "输出看起来对" | 必须检查退出码和完整输出 |

## 完成检查清单

- [ ] 验证命令已实际运行（不是回忆之前的结果）
- [ ] 完整输出已读取，退出码已检查
- [ ] 失败用例数量为 0
- [ ] spec 校验通过（valid: true）
- [ ] 对抗性验证子代理已派发且无法推翻结论
- [ ] 没有使用"应该"、"大概"、"似乎"等模糊词语

## 禁止用语

<EXTREMELY-IMPORTANT>
禁止使用以下词语：
- "should"、"probably"、"seems"
- "应该"、"大概"、"似乎"

使用这些词语意味着你没有验证。
</EXTREMELY-IMPORTANT>

## 常见失败模式

| 声称 | 需要 | 不充分 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 失败 | 之前运行、"应该通过" |
| 构建成功 | 构建命令：exit 0 | linter 通过、日志看起来正常 |
| Bug 已修复 | 原始症状测试：通过 | 代码已改、假设已修复 |
| 需求已满足 | 逐项检查清单 | 测试通过 |
