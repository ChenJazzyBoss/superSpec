# superSpec: Subagent-Driven Development

执行多任务实现计划，每个任务包含双重 review。

## 使用时机

当你有一个实现计划需要执行时，使用此技能。

## 每个任务的强制流程

<EXTREMELY-IMPORTANT>
你必须为每个任务完成以下步骤，不可跳过：
</EXTREMELY-IMPORTANT>

1. **预提取**：主 AI 预提取任务文本和上下文
2. **派发实现者**：派发实现子代理（完整任务文本 + 上下文）
3. **处理问题**：处理子代理问题（在实现前回答）
4. **实现**：实现者实现、测试、提交、自检
5. **spec 合规审查**：派发 spec 合规审查子代理
   - 运行 `superspec validate` 确认 spec 仍然合法
   - 检查代码实现是否符合 spec 需求（完整性 + 正确性 + 一致性）
6. **修复循环**：如有问题，实现者修复 → 重新审查（循环直到通过）
7. **代码质量审查**：派发代码质量审查子代理
   - 检查代码风格、错误处理、边界情况
8. **修复循环**：如有问题，实现者修复 → 重新审查（循环直到通过）
9. **标记完成**：标记任务完成

## HARD-GATE 门禁

<HARD-GATE>
禁止以下行为：
- 禁止在 main 分支上直接开发
- 禁止跳过 spec 合规审查或代码质量审查
- 禁止在有未解决问题时继续
- 禁止并行派发多个实现子代理
- 禁止在 spec 合规审查通过前开始代码质量审查
</HARD-GATE>

## 实现者状态处理

| 状态 | 行动 |
|------|------|
| DONE | 进入 spec 合规审查 |
| DONE_WITH_CONCERNS | 读取关注点，正确性/范围问题需修复 |
| NEEDS_CONTEXT | 提供缺失上下文，重新派发 |
| BLOCKED | 分析原因（上下文/模型/任务过大/计划问题） |

## 模型选择策略

- **机械任务**（1-2 文件，明确 spec）：便宜/快速模型
- **集成任务**（多文件，调试）：标准模型
- **架构/审查任务**：最强模型

## 子代理 Prompt 模板

### 实现者 Prompt

```markdown
你是实现者。你的任务是实现以下功能：

## 任务
<完整任务文本>

## 上下文
<项目结构、相关文件、spec 需求>

## 要求
1. 遵循 TDD：先写失败测试，再写实现
2. 测试通过后提交
3. 自检：代码是否符合 spec 需求

## 状态报告
完成后报告：
- DONE：实现完成
- DONE_WITH_CONCERNS：有关注点需要讨论
- NEEDS_CONTEXT：需要更多信息
- BLOCKED：无法继续
```

### spec 合规审查者 Prompt

```markdown
你是 spec 合规审查者。你的任务是检查实现是否符合 spec 需求。

## 检查清单
1. 运行 `superspec validate` 确认 spec 仍然合法
2. 检查完整性：所有需求都有对应实现
3. 检查正确性：实现符合 spec 意图
4. 检查一致性：代码结构与 spec 结构对应

## 输出
- PASS：实现符合 spec
- FAIL：列出不符合的地方
```

### 代码质量审查者 Prompt

```markdown
你是代码质量审查者。你的任务是检查代码质量。

## 检查清单
1. 代码风格是否一致
2. 错误处理是否完整
3. 边界情况是否处理
4. 是否有潜在的 bug

## 输出
- PASS：代码质量合格
- FAIL：列出需要改进的地方
```

## 跳步红线

| 跳步借口 | 现实 |
|----------|------|
| "子代理说完成了，应该没问题" | 子代理可能幻觉完成，必须验证 |
| "这个任务很简单，不需要审查" | 简单任务也会出错，审查不能跳 |
| "审查太慢了，直接下一个" | 跳过审查会导致错误累积 |
| "子代理遇到了问题，我来直接改" | 应该提供上下文让子代理自己修 |
| "测试跑过了，应该没问题" | 测试通过不代表符合 spec |

## 完成检查清单

- [ ] 每个任务都经过实现 → spec 合规审查 → 代码质量审查三步
- [ ] 子代理输出包含明确的状态标记（DONE/DONE_WITH_CONCERNS/NEEDS_CONTEXT/BLOCKED）
- [ ] spec 合规审查运行了 `superspec validate`
- [ ] 所有审查 FAIL 都有对应的修复循环
- [ ] 没有在 main 分支上直接开发
- [ ] 没有并行派发多个实现子代理
