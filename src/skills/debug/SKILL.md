# superSpec: Debug

spec 感知的系统化调试。调试时引用 spec 需求作为上下文。

## 使用时机

当你遇到 bug 或测试失败时，使用此技能。

## 4 阶段调试流程

<EXTREMELY-IMPORTANT>
你必须按顺序完成以下 4 个阶段：
</EXTREMELY-IMPORTANT>

### 阶段 1：根因调查

1. 读取相关 spec 需求，理解预期行为
2. 反向追踪调用栈
3. 定位偏差发生的位置

### 阶段 2：模式分析

1. 查找代码库中的相似问题
2. 检查是否有系统性问题

### 阶段 3：假设与验证

1. 提出假设
2. 设计实验验证假设
3. 记录实验结果

### 阶段 4：实现修复

1. 编写失败测试重现问题
2. 实现修复
3. 运行 `superspec validate` 确认 spec 合规

## 3 次失败规则

<HARD-GATE>
连续 3 次修复尝试失败后，必须停下来质疑架构，而非尝试第 4 次。

质疑方向：
- 架构设计是否有问题？
- 需求理解是否有误？
- 是否需要更强的模型？
- 任务是否需要拆分？
</HARD-GATE>

## 跳步红线

| 跳步借口 | 现实 |
|----------|------|
| "再试一次应该就好了" | 3 次失败后必须停下来质疑架构 |
| "我知道问题在哪" | 知道不等于验证了，先读代码 |
| "这个 bug 很小" | 小 bug 也可能有大根因 |
| "我改了一行代码" | 一行代码也可能有大影响 |
| "不看错误信息了，直接改" | 错误信息是最重要的线索 |
| "假设性修复，先试试" | 必须先验证假设再修复 |
| "这个文件应该没问题" | 必须读代码确认，不能假设 |

## 完成检查清单

- [ ] 已读取相关 spec 需求，理解预期行为
- [ ] 已反向追踪调用栈，定位偏差位置
- [ ] 假设有实验验证，不是猜测
- [ ] 编写了失败测试重现问题
- [ ] 修复后测试通过
- [ ] `superspec validate` 确认 spec 合规
- [ ] 如果连续 3 次失败，已停下来质疑架构

## 调试记录

每次调试都应记录：

```markdown
## 调试记录

**问题**：<描述>

**假设**：
1. <假设 1> → 验证结果：<通过/失败>
2. <假设 2> → 验证结果：<通过/失败>

**根因**：<最终根因>

**修复**：<修复方案>
```

## 下一步

调试完成后，推荐：
- **返回之前失败的技能**，继续执行
- 使用 `verify` 验证修复是否有效
- 使用 `pipeline next debug` 查看推荐路径
